# Development

## Architecture

The firmware is a plain Arduino sketch in `firmware/LedLetters/`. `loop()` calls four modules in turn;
none of them blocks.

| Module | Responsibility |
|---|---|
| `config.h` | Pins, limits (glyphs, LEDs per glyph), network names, defaults. |
| `layout.*` | Builds the sign at boot from the saved glyph list and computes where every LED is. |
| `effects.*` | Effect engine: ~60 fps, cross-fades between effects, smooth power on/off, current limit. |
| `settings.*` | Settings in flash (ESP32 Preferences, namespace `mk`), saved 3 s after the last change. |
| `net.*` | Wi-Fi, setup hotspot with captive portal, mDNS, web server and the [API](api.md). |
| `web_ui.h` | The phone app, one self-contained HTML page (no external fonts or scripts, so it works from the hotspot with no internet). |
| `glyph_data.h` | Generated glyph catalog. |

### The sign layout

The sign is stored as a list of glyphs in chain order with their real LED counts:

```
Heart:27,M:30,Amp:27,K:22
```

Names are the glyph names in `glyph_data.h` (`A`–`Z`, `0`–`9`, `Amp`, `At`, `Hash`, `Heart`). At boot
`layoutInit()` places the glyphs left to right and spreads each glyph's LEDs along its LED path,
in proportion to the design counts of its segments. That gives every LED:

| Table | Meaning |
|---|---|
| `ledX`, `ledY` | Position on the whole sign, 0–255 (y = 0 at the top). |
| `ledR` | Distance from the centre of the sign, 0–255. |
| `ledSymbol`, `ledSeg` | Which glyph and which segment of it the LED belongs to. |

Effects use these instead of the LED index, so a sweep moves across the sign and fire rises,
whatever the wiring inside each glyph. An empty list means "not set up yet": the firmware drives a
plain 150-LED strip until the glyphs are saved.

Limits, in `config.h`: at most `MAX_GLYPHS` (6) glyphs, `MIN_GLYPH_LEDS`–`MAX_GLYPH_LEDS` (2–60) LEDs
each. The app warns above `WARN_GLYPHS` (4).

### Glyph catalog

`glyph_data.h` is generated by `tools/gen_glyphs.py` from `led_map.json` in the glyph design files
(the 3D model project that also produces the printable files and the soldering guide). For every
glyph it holds:

- `leds`: the planned LED count (the app's default).
- `steps[]`: the strip pieces in **wiring order**, from IN to OUT, each with its LED count and
  `leds_xy`, the centre of every LED in data order (mm, origin at the glyph's bottom-left).

Each step becomes one segment of the glyph, in the same order, so LED index → position matches the
real wiring. At the planned count every LED is placed exactly at its centre; with a different count
(entered by the user in the app) the LEDs are spread along the same path.

```bash
python3 tools/gen_glyphs.py path/to/glyph-design-files
```

The generator stops with an error if a glyph's steps don't add up to its LED count.

### Adding a glyph

1. Add it to the design files, so `led_map.json` has its LED count, size and steps.
2. Run the generator and rebuild. The glyph appears in the app automatically.
3. If it should beat in Heartbeat, add its name to `PULSES`.

### Adding an effect

1. Write a function in `effects.cpp` that fills `fx[0..numLeds-1]`, using `T` (effect time in ms,
   scaled by the speed setting), `S.color1` / `S.color2`, and the layout tables.
2. Add it to `MODES[]`. Keep **Mixed** second to last and the test mode last (`MIXED_MODE` relies on
   it), and check the default per-glyph effects in `settings.h`.
3. Add a matching case to `colour()` in `web_ui.h` so the app preview shows it.

## The phone app without a board

`tools/mock_server.py` serves `web_ui.h` with a fake API, so the app can be changed and checked in a
desktop browser:

```bash
python3 tools/mock_server.py      # http://localhost:8080
```

- `http://localhost:8080/?fresh` starts as a brand-new controller (no glyphs).
- `http://localhost:8080/?ap` pretends the phone is on the setup hotspot; any non-empty Wi-Fi
  password "joins" after 4 seconds.

The page is read from `web_ui.h` on every load; restart the server after editing the Python.

## Network behaviour

```
power on ── saved Wi-Fi? ──no──────────────────────────► hotspot "LED-Letters-Setup"
                │yes                                       (10 min, kept open while a phone is
                ▼                                            connected; then retries Wi-Fi every 2 min)
          join (20 s) ──fails──────────────────────────►  hotspot
                │ok
                ▼
          on home Wi-Fi: http://led-letters.local, hotspot off
```

- Joining from the hotspot keeps the hotspot up while the controller tries the network, reports the
  result and the new IP to the app, and keeps the hotspot for 2 more minutes so the phone can show it.
- Transmit power is reduced to 8.5 dBm; many ESP32-C3 SuperMini boards cannot connect at full power.
- The web server must start after Wi-Fi (`netSetup()`); the other order crashes at boot.

## Button

The on-board BOOT button (GPIO 9): short press = next effect (or turn on), hold about 1 s = power
on/off, hold 6 s = forget Wi-Fi (blinks blue) and restart into the hotspot.

## Settings keys

Namespace `mk`: `on`, `md` (effect), `bri`, `spd`, `c1`, `c2`, `auto`, `ma` (current limit, mA),
`sign` (glyph list), `sm` (per-glyph effects). Namespace `wifi`: `ssid`, `pass`.
